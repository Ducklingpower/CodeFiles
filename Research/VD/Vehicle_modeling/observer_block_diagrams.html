0 · What the package computes

Four stages. The kinematics give the reference slips and the slip ratios. The load model and the strain gages give the observed normal load. The force balance and the wheel dynamics give the forces. The slip observers turn the axle force and the observed load into slip angles without the localization vy, and those give the understeer gradient.

–odom vx, vy, r, attitude: /odometry/global_filtered3 Hz (fc); 0.3 Hz copy for the load model (fcObsModel)kinematics (vy: the reference slips only), force balance and load model (vx, r, attitude), observers (vx, r)

–brake pressures, rpm, throttle, gear: brake_2_report, pt_report3 Hz (gear unfiltered)wheel dynamics Fx

Every filter is a first order Tustin low pass with prewarp (lpf, vehicle_model.m:998): K = tan(π fc Ts), y(k) = (1−K)/(1+K)·y(k−1) + K/(1+K)·(x(k) + x(k−1)), Ts = 0.01 s. Derivatives are backward differences of filtered signals (ddt, :273).

1 · Road wheel angles and kinematic slips

Every tire uses its own road wheel angle. The steering wheel angle goes through the steering ratio and offset, then the Ackermann table gives the left and right front angle, and the static toe is added on top (0 until it is confirmed on the car). The bicycle model uses the mean of the two front angles.

4 · Bicycle vy observer (MPC brush at the observed axle load)

The MPC brush tire inverts the axle force at the observed axle load into an axle slip. Kinematics turn the two slips into a vy, the IMU integrates vy between corrections. The localization vy is not an input. Full trust: the tire model vy is the mean of the two axles.

5 · Per tire Fy, dual track vy observer and kus

The axle force is split per tire twice: by normal load, and by normal load corrected with each tire's brush at the dual track observer's own slip of the previous sample (Jung & Choi). dualTrackObserver runs one sample at a time, like the C++ DualTrackModel::step, and the dual track model takes nothing from the bicycle model. The corrected split is the per tire Fy output and the input of the dual track observer. The understeer gradient uses the controller's formula with a secant axle stiffness; the right column shows where the bicycle version differs.

7 · Building the on-vehicle vehicle_model package

Target: on-vehicle/src/control/vehicle_model, rebuilt as one node that wraps two model classes (Fig. P2). This section is written so an engineer or an agent can start cold: the rules, the file layout, the node structure, the model API, the MATLAB to C++ map, then the phases.

7.1 · Rules

Read first

The math is vehicle_model.m, exactly

  • Every equation, constant, gate, clamp and flag the package uses is in vehicle_model.m and the C++ must give the same numbers. No extra filtering, no extra clamps, no "improvements" in the C++. A change goes into vehicle_model.m first (and into this page and the README), then the C++ follows, and the bag replay comparison (Phase 3 of 7.6) is run again.
  • What is in the package: everything in vehicle_model.m above the section NOT IN THE PACKAGE (line 537): settings and parameters, calibrations (as parameters), input conditioning, the SHARED, STATELESS sections, the BICYCLE MODEL sections and the DUAL TRACK MODEL sections, plus the functions they call. Below that line (alphaB, the weighted observer, kus measured, the Fx IMU split, the save, the plots) is research only.
  • The two models share no state and never read each other's outputs. They share stateless functions only. Each has its own Fz observer instance and its own vy observer state.
  • The node holds no model math. It subscribes, checks message timeouts, conditions the inputs (units, calibrations, filters, road wheel angles) into one input struct, runs both models on the same sample, publishes their outputs and its own errors.
  • Same names and units as MATLAB. Parameter names follow vehicleParams in snake_case; SI and radians everywhere; signs as MATLAB (α > 0 → Fy > 0, δ > 0 = left turn, the controller's brush sign flipped in brushFy).
  • Verification is a bag replay: the comp2 bag played at 1× through the node, the recorded outputs converted to CSV and plotted against vehicle_model.m run on the same log (Phase 3 of 7.6).
  • Nothing changes for the car until the consumers are switched on purpose (shadow mode, Phase 4).

void VehicleModelNode::controlCallback()
{
    if (!bicycle_ || !dual_track_) {return;}

    checkMsgTimeouts();                 // ErrorReport, sets input_valid_ / gage_valid_ / fx_valid_
    if (!input_valid_) {return;}

    conditioner_.update(raw_, model_input_);   // units, calibrations, Tustin filters, road wheel angles

    bicycle_->setInput(model_input_);
    bicycle_->step();
    dual_track_->setInput(model_input_);
    dual_track_->step();

    publishBicycle(bicycle_->getOutput(), bicycle_->getDebug());
    publishDualTrack(dual_track_->getOutput(), dual_track_->getDebug());
}

void VehicleModelNode::checkMsgTimeouts()
{
    blackandgold_msgs::msg::ErrorReport error_msg;
    error_msg.header.stamp = this->now();
    error_msg.origin = "vehicle_model_node";
    error_msg.module = "control";
    error_msg.lifetime = 1.0;

    input_valid_ = true;
    if ((this->clock->now() - this->last_odom_time_).seconds() > max_msg_timeout_s) {
        input_valid_ = false;
        error_msg.description = "Odometry message timeout! Vehicle model outputs invalid.";
        error_msg.severity = blackandgold_msgs::msg::ErrorReport::ERROR_FATAL;
    }
    // ... accel, steering, wheel speed (fatal); tire_report, brake, pt (soft fault) the same way

    if (!input_valid_ || soft_fault_) {
        pubError_->publish(error_msg);
    }
}

7.6 · Phases

Phase 1

C++ blocks and the two model classes, no ROS

  1. Filters: a Tustin prewarped first order low pass to match lpf (the node's current lowPassFilter is the exponential form, slightly different); 3 Hz shared, 0.3 Hz load model inputs, 0.5 Hz gages and the model compare copy.
  2. Road wheel angles: load the Ackermann table as a CSV parameter, linear interpolation, toe parameters; δi for all four tires and the bicycle δ.
  3. Kinematics: one tire_kin(vx, vy, r, δ[4]) used for the reference slips, the slip ratios and both observers; replace the single steering angle in calculate_slip_angles and slip_ratio_calc with δi.
  4. Load model: the bicycle loads with a_z = g·cosθ·cosφ − v_x·r·sinφ (the C++ bicycle model has the bank term commented out), downforce, the dual track lateral transfer and the corner split.
  5. Fz observer: one class, two instances with their own state (axle in the bicycle model, per tire in the dual track model), the model passed through the gage filter before the rate compare; c(k) = a·(c(k−1) + K·u). The existing vehicle_model::Observer computes c = (1−leak)·c + K·e, which matches with leak = 1 − τ/(τ + dt) = 0.00125 and K_c++ = K·τ/(τ + dt) = 1.0986 at τ 8 s, K 1.1, dt 0.01 s.
  6. Forces: axle Fy force and yaw moment balance with the front in its tire frame; Fx total; Fx per tire from the wheel dynamics (engine map CSV, gear and diff ratios and efficiencies, brake gain, inertias, locked cap at μx times the load model Fz, so it stays stateless and shared).
  7. Brush: forward, closed form inverse, conditioning and the load sensitive Cα_i = Cα/2·(F_z,i/F_z0)^p as one small header; the same header in fbl_mpc_controller so the controller and the package use one tire model (the closed form equals its cubic).
  8. Two model classes on those functions, each with its own state and one step(): BicycleModel::step() (after setInput(in), read with getOutput() / getDebug()) (axle kinematics, axle load model + Fz observer, axle forces, bicycle vy observer, kus) and DualTrackModel::step() (same API) (tire kinematics and slip ratios, tire load model + Fz observer, Fx per tire, Fy split + correction at its own previous-sample slip, dual track vy observer, kus). Neither reads the other.
  9. Build in the order of the MATLAB sections (7.5); each block is a line for line port of its section.
Phase 2

Node, parameters, messages

  1. One node as the wrapper: subscriptions → input conditioning (units, calibrations, filters, road wheel angles) into VehicleModelInput → bicycle_->step(), dual_track_->step() → publish. The node holds no model math.
  2. Subscriptions: /odometry/global_filtered, /novatel_bottom/accel_filtered, steering_extended_report, wheel_speed_report, tire_report, brake_2_report, pt_report; one 100 Hz update.
  3. Parameters from vehicle_model.m: lf 1.724 / lr 1.248 m (URDF base_link), tracks, m, h, Iz, aero, roll centres and wheel rates, steering ratio and offset, Ackermann table, toe, brush μ, Cα, Fz0 and p (0.76 / 0.78 from the rig .tir), observer τ, K, the dual track weights switch (off) and speed gates.
  4. Messages: BicycleState, BicycleDebug, DualTrackState, DualTrackDebug in blackandgold_msgs (fields in the table above); each model returns its state and debug struct from step(), the node copies them into the messages and publishes errors itself.
Phase 3

Verify: replay the comp2 bag through the node, compare with vehicle_model.m

  1. MATLAB side: vehicle_model.m on bags/lagoona/comp2/compition_bags/2026-09-03_121638_merged.csv, which is rosbag2_merged_2026-09-03_121638 merged by merge_rosbag2_folder_to_csv_v3.py onto a 0.01 s grid (merge report: t0 = 1788463010.696 s, no filter).
  2. C++ side: ros2 bag play rosbag2_merged_2026-09-03_121638 --clock 200 at 1× speed (/clock at 200 Hz, the default 40 Hz is coarser than the node's timer) (the node runs on a 100 Hz timer and checks message timeouts, so a faster replay is not the same experiment), playing only the input topics (leave the bag's own /control/vehicle_model/* out), with the node on use_sim_time:=true; ros2 bag record --use-sim-time -s mcap (the merge script reads mcap only) the four output topics and /control/vehicle_model/errors (the merge script times every sample by the recorder's log time, so the recorder must run on bag time too).

  4. Convert the recorded bag: python3 merge_rosbag2_folder_to_csv_v3.py -i <recording> -o <out> -t 0.01 --time-mode union --topics-file vehicle_model_node_topics.yaml, with the workspace sourced so the new blackandgold_msgs types decode, and no -f (that filter is zero phase and would change the outputs). vehicle_model_node_topics.yaml (in Vehicle_modeling/) maps every message field to a CSV column; if the messages change, change it and the signal list in the comparison script together. The CSV time_s is absolute bag time, the same clock as the comp2 CSV (which starts at 1788463010.696 s).
  5. Compare in MATLAB with plots: node vs vehicle_model.m for every output (road wheel angles, slips, slip ratios, Fz, Fx, Fy, vy, observed slips, kus, debug flags), overlay plus the difference, whole log and the fastest lap with C1 to C11 marked: compare_vehicle_model_node.m. It runs vehicle_model.m (plots off), reads the node CSV (nodeCsv at the top), interpolates it onto the MATLAB samples (linear, flags previous), scores only where MATLAB is finite, and prints per signal: rms and p99 of node − MATLAB, rms / rms, the best lag within ±0.5 s and the rms at that lag (a pure timing offset shows as a lag with a small rms at lag; a math error keeps a large rms at lag), and the % of samples where each debug flag disagrees. Tabs: summary bars, one tab per group (overlay | difference), fastest lap. Tested on a synthetic node CSV (10 ms delay, noise, a 5 % kus error, flipped flags, a missing column): all four were found.
  6. What to expect: the MATLAB inputs are linearly interpolated onto a fixed 10 ms grid while the node sees each message at its own rate and steps on its own 100 Hz timer with the latest values, so the two differ at the noise level even when the code is right. A real mismatch shows as an offset, a sign, a lag, a drift or a diverging observer in the difference trace.
